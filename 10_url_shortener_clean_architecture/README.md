# 10_url_shortener_clean_architecture: 短縮URL（クリーンアーキテクチャ）

## 🎯 この章のねらい
お題は小さくして、**層の分け方と依存の向き**の練習に集中します。お題は「短縮URL」です。05と同じく**テストを先に書き**、Red → Green → Refactor の小さな歩幅で層を育てます。

- 言語は **Python**、テストは **pytest**
- 標準ライブラリだけを使う
- 層（domain / usecases / adapters / main）に分け、依存は**内側へだけ**向ける
- 外側（保存先・コード生成・入口）を差し替えても、内側のコードが変わらないことを確かめる

---

## 📖 要求

| # | 要求 |
| --- | --- |
| 1 | 長いURLを渡すと、短いコードを返す |
| 2 | コードを渡すと、元のURLを返す |
| 3 | 同じURLを2回短縮したら、同じコードを返す |
| 4 | 不正なURL（http/https 以外など）は受け付けない |
| 5 | ✅【発展】入口を CLI に加えて HTTP（`http.server`）でも使える |

> 要求は進めながら増減してOKです。決めたことは `DESIGN.md` に反映します。

---

## 🧭 設計の考えどころ（答えは書きません）

1. **依存の向き**: `domain` は何を import してよい？ `usecases` は具象の保存先を知ってよい？
2. **URL の妥当性検査**: ドメインのルール？ ユースケースの仕事？ 入口の仕事？
3. **インターフェースの置き場所**: `UrlRepository` や `CodeGenerator` の `Protocol` は、どの層のファイルに置く？
4. **ユースケースの入出力**: 専用のデータ型にする？ ドメインのオブジェクトをそのまま返す？
5. **エラーの変換**: 「存在しないコード」「不正なURL」を、CLI のメッセージや終了コードに変えるのはだれ？
6. **組み立て役**: 具象クラスを知っている場所を、1か所だけにできる？
7. **テストのしやすさ**: ユースケースを、ファイルも CLI もなしでテストできる？
8. **TDDの歩幅**: 最初のテストは内側（domain）から？ 外側（CLI）から？ 層は**テストが分けたがったとき**に分ける
