# クリーンアーキテクチャの層の考え方

## 1. 何のために層に分けるのか

クリーンアーキテクチャは、Robert C. Martin が提唱した設計の型である。
この型は、プログラムのコードを**変わる理由ごとに**層へ分ける。

コードが変わる理由には、性質の違う2種類がある。

- **業務の都合**: 「同じURLは同じコードにする」のような、アプリが何をするかの決まりが変わる
- **技術の都合**: 保存先をメモリからファイルに替える、入口を CLI から HTTP に替える、といった手段が変わる

業務の決まりのコードと技術の手段のコードが混ざっていると、保存先を替えるだけで業務の決まりのコードまで書き直すことになる。
クリーンアーキテクチャは、両者を別の層に置き、**技術の都合で業務のコードが変わらない**ようにする。

## 2. 4つの層

層は同心円で描かれる。内側の層ほど業務の中心に近く、変わりにくい。外側の層ほど技術の手段に近く、変わりやすい。

```
┌───────────────────────────────────────────┐
│ Frameworks & Drivers（DB・Web・CLI の道具）│
│ ┌───────────────────────────────────────┐ │
│ │ Interface Adapters（変換係）          │ │
│ │ ┌───────────────────────────────────┐ │ │
│ │ │ Use Cases（アプリの手順）         │ │ │
│ │ │ ┌───────────────────────────────┐ │ │ │
│ │ │ │ Entities（業務の決まり）      │ │ │ │
│ │ │ └───────────────────────────────┘ │ │ │
│ │ └───────────────────────────────────┘ │ │
│ └───────────────────────────────────────┘ │
└───────────────────────────────────────────┘
```

| 層 | 置くもの | この層が変わる理由 |
| --- | --- | --- |
| Entities | 業務の決まりと、それを守る値やオブジェクト | 業務の決まりそのものが変わったとき |
| Use Cases | アプリが行う手順。Entities を使って1つの操作をやり遂げる | アプリの振る舞いが変わったとき |
| Interface Adapters | 外の世界の形式とユースケースの形式を変換するコード。保存先の実装、CLI の引数の読み取りなど | 外の世界とのやりとりの形式が変わったとき |
| Frameworks & Drivers | データベース、Web フレームワーク、ファイルシステムなどの道具と、それを呼ぶ薄いコード | 道具を替えたとき |

### Entities

Entities は、アプリがなくても成り立つ業務の決まりを表す。
この層のコードは、ほかのどの層のコードも import しない。
本章では、`Url` が「http/https で、ホスト名がある」という決まりを守る。

### Use Cases

Use Cases は、利用者がアプリにさせたい操作を1つずつ表す。
ユースケースは、Entities を使い、保存先などの外の部品に指示を出して、操作を最後までやり遂げる。
ユースケースは、外の部品が**何であるか**を知らない。メモリに保存するのかファイルに保存するのかを、ユースケースは区別しない。
本章では、`ShortenUrl` と `ResolveUrl` がこの層に入る。

### Interface Adapters

Interface Adapters は、外の世界とユースケースのあいだでデータの形を変換する。
たとえば、CLI のアダプターは、コマンドライン引数の文字列を読み取り、ユースケースを呼び、結果を画面用の文字列にする。
保存先のアダプターは、ユースケースから受け取った値を `dict` やファイルの形式で書き留める。
本章では、`InMemoryUrlRepository` や CLI がこの層に入る。

### Frameworks & Drivers

Frameworks & Drivers は、データベースや Web フレームワークそのものである。
開発者がこの層に書くコードは少なく、多くは道具を呼び出す薄いコードになる。
本章は標準ライブラリだけを使うので、この層を Interface Adapters とまとめて `adapters` と呼ぶ。

## 3. 依存のルール

クリーンアーキテクチャの規則は、次の1つにまとまる。

> **ソースコードの依存は、内側へだけ向ける。**

ここでいう「依存する」は、「相手の名前をコードに書く」ことを指す。Python では、`import` 文、クラス名、関数名を書くことがこれにあたる。

- 外側の層は、内側の層を import してよい
- 内側の層は、外側の層を import してはいけない。外側にあるクラスの名前も関数の名前も、内側のコードに書かない

このルールを守ると、外側の層を差し替えても内側の層のコードは1行も変わらない。内側のコードは外側の名前を1つも書いていないからである。

## 4. 内側が外側の部品を使うとき（依存性逆転）

ここで1つ問題が起きる。
`ShortenUrl`（Use Cases）は、コードを保存先（Interface Adapters）に書き留めなければならない。処理の流れは内側から外側へ向かう。
しかし、依存のルールにより、`ShortenUrl` は `InMemoryUrlRepository` を import できない。

この問題は、**内側の層が約束ごとを定義し、外側の層がその約束ごとを満たす**ことで解決する。

```python
# usecases.py（内側）: 保存先に求める操作を、内側が決める
class UrlRepository(Protocol):
    def save(self, code: str, url: str) -> None: ...
    def find(self, code: str) -> str: ...

class ShortenUrl:
    def __init__(self, repository: UrlRepository): ...   # 約束ごとの名前だけを書く
```

```python
# adapters.py（外側）: 内側の約束ごとに合わせて作る
class InMemoryUrlRepository:
    def save(self, code: str, url: str) -> None: ...
    def find(self, code: str) -> str: ...
```

（メソッド名は説明用である。本章の実際の名前は T1 で決める。）

この形では、処理は内側から外側へ流れるが、import の矢印は外側から内側へ向くか、どこにも向かない。

```
処理の流れ:  ShortenUrl ──呼ぶ──▶ InMemoryUrlRepository
名前の参照:  ShortenUrl ──書く──▶ UrlRepository ◀──形を合わせる── InMemoryUrlRepository
```

処理の向きと依存の向きが逆になるので、この技法を**依存性逆転**（Dependency Inversion）と呼ぶ。
約束ごとを定義するのは、使う側（内側）である。使われる側（外側）ではない。

## 5. 組み立て役（main）

内側の層は、具象クラスの名前を書かない。そのため、だれかが具象クラスを作って内側に渡さなければならない。
この仕事を担うのが**組み立て役**（main）である。main は最も外側に置かれ、すべての層を import してよい。

```python
# main.py
repository = InMemoryUrlRepository()
generator = RandomCodeGenerator()
shorten = ShortenUrl(generator=generator, repository=repository)
```

具象クラスの名前は、main の1か所にだけ現れる。保存先をファイル版に替えるときは、main の1行を書き換えればよい。

テストも組み立て役の一種である。テストは、本物の代わりに `FixedCodeGenerator` のような偽物を作り、ユースケースに渡す。
ユースケースは約束ごとしか知らないので、本物と偽物を区別しない。

## 6. 境界を越えるデータ

層の境界を越えて渡すデータは、受け取る側の層が知っている型にする。
外側の層は、`str` や `int` のような単純な型、または内側の層が定義した型を内側へ渡す。
内側の層は、外側の層の型（たとえばデータベースの行オブジェクトや HTTP リクエスト）を受け取らない。

## 7. 本章の対応

| クリーンアーキテクチャの層 | 本章のモジュール | 主な登場人物 |
| --- | --- | --- |
| Entities | `domain.py` | `Url`, `InvalidUrlError` |
| Use Cases | `usecases.py` | `ShortenUrl`, `ResolveUrl`, `UrlRepository`, `CodeGenerator` |
| Interface Adapters + Frameworks & Drivers | `adapters.py` など | `InMemoryUrlRepository`, `RandomCodeGenerator`, CLI |
| 組み立て役 | `main.py` | 具象クラスを作ってユースケースに渡すコード |

本章は、Martin の原典にある入力ポート・出力ポート・Presenter を省いている。
本章のユースケースは、結果を戻り値でそのまま返す。
